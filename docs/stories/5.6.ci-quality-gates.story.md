# 5.6: CI gates: PHPStan + Pest pass before merge

**Story ID:** 5.6
**Epic:** 5 — Code Quality & Infrastructure
**Slug:** ci-quality-gates
**Status:** backlog

## Story

As the tech lead accountable for code quality on `dev`,
I want the existing `phpstan`, `pint`, and `tests` jobs in `.github/workflows/ci.yml` to actually block merge on failure,
so that PHPStan Level 10 errors and failing/under-covered Pest runs can no longer reach `dev` just because every quality step currently ends in `|| true`.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. The `phpstan` job in `.github/workflows/ci.yml` runs `./vendor/bin/phpstan analyse Modules --level=10 --memory-limit=1G --no-progress` without a trailing `|| true`, so a non-zero PHPStan exit code fails the job. [Source: prd.md#NFR-CQ-001 — "Enforcement: CI gate blocks merge if PHPStan L10 fails"]
2. The `tests` job runs `php artisan test --no-interaction --coverage --min=82` (or equivalent) without a trailing `|| true`, so both a failing test and coverage below 82% fail the job. [Source: prd.md#NFR-CQ-002 — "CI gate: fail if coverage drops below 82%"]
3. The repository's branch protection (or, if branch protection is out of the dev agent's reach, a documented required-checks list in this story's Dev Notes handoff) names `phpstan` and `tests` as required status checks on the `dev` branch. [Inference — NFR-CQ-001/002 require a "CI gate blocks merge," which on GitHub is implemented via required status checks, not merely a job existing]
4. The `pint` job's formatting check may remain non-blocking (`|| true` retained) unless the dev agent is separately instructed otherwise — Pint style is out of this story's cited scope. [Inference — no PRD/architecture NFR names code-style formatting as a blocking gate, only PHPStan and coverage]
5. The `theme-build` job is unmodified by this story — its build step is unrelated to the PHPStan/Pest gates this story targets. [Inference — scope boundary, no NFR ties theme build to the CQ gates]
6. This story does not modify `laravel/phpstan.neon`; the PHPStan level/config enforced by CI remains whatever the existing neon file already specifies. [Source: docs/wiki/rules/phpstan-neon-immutable.md — "Solo l'UTENTE umano può modificarlo. Gli agenti AI mai."]

## Tasks / Subtasks

- [ ] Edit the `phpstan` job step in `.github/workflows/ci.yml` to remove the trailing `|| true` from the `./vendor/bin/phpstan analyse Modules --level=10 --memory-limit=1G --no-progress` command (AC: #1)
- [ ] Edit the `tests` job step to remove the trailing `|| true` from `php artisan test --no-interaction`, and add `--coverage --min=82` using the existing `coverage: xdebug` setup already configured on that job (AC: #2)
- [ ] Confirm the `pint` and `theme-build` jobs are left as-is, with no `|| true` removed from `pint` and no edits to `theme-build` (AC: #4, #5)
- [ ] Document the required-status-check names (`phpstan`, `tests`) that branch protection on `dev` must list, in this story's Dev Notes handoff for whoever configures GitHub branch protection (AC: #3)
- [ ] Confirm `git diff --stat laravel/phpstan.neon` is empty after this story (AC: #6)
- [ ] Verify story 5.1 (User/Lang PHPStan debt) and 5.2 (Pest baseline coverage) have landed before flipping these gates live, per Dependency Maps below (AC: #1, #2)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Current CI state (verbatim job structure):** `.github/workflows/ci.yml` defines 4 jobs — `phpstan` runs `./vendor/bin/phpstan analyse Modules --level=10 --memory-limit=1G --no-progress || true`; `pint` runs `./vendor/bin/pint --test || true`; `tests` runs against a MySQL 8.0 service with `DB_DATABASE: laravelpizza_test`, `coverage: xdebug`, and `php artisan test --no-interaction || true`; `theme-build` builds `laravel/Themes/Sixteen`. Every quality-check step currently ends `|| true`, so none of them can fail the workflow. [Source: .github/workflows/ci.yml]
- **Narrower companion workflow:** `.github/workflows/quality.yml` triggers only on `paths: laravel/Modules/Activity/**` and runs PHPStan/PHPMD/Pint/PHPInsights against `Modules/Activity` only, with the same `|| true` pattern on every step — this story does not touch `quality.yml`; it is out of scope (Activity-only, narrower than the Epic 5 project-wide gate). [Source: .github/workflows/quality.yml]
- **Requirement driving AC #1:** "PHPStan Level 10 (0 errors), all 35 modules... Enforcement: CI gate blocks merge if PHPStan L10 fails." [Source: prd.md#NFR-CQ-001]
- **Requirement driving AC #2:** "Target: ≥85% code coverage (from baseline 65%)... Tools: Pest + Xdebug coverage reports... CI gate: fail if coverage drops below 82%." [Source: prd.md#NFR-CQ-002]
- **phpstan.neon is immutable by agents:** "Unico file di config PHPStan del progetto: `laravel/phpstan.neon`... Solo l'UTENTE umano può modificarlo. Gli agenti AI mai." This story only removes `|| true` from the CI step invoking the existing neon config — it must not add `-c`, `--level`, or any new neon file. [Source: docs/wiki/rules/phpstan-neon-immutable.md]
- [Inference] GitHub Actions branch protection ("required status checks") is a repository setting, not a file this dev agent can always edit via a code change — if the dev agent lacks admin access to configure it, this story's job is to make the CI jobs *capable* of failing (AC #1/#2) and to document the exact check names needed (AC #3), handing the actual branch-protection toggle to whoever has repo admin rights.
- [Inference] This story assumes 5.1 (User/Lang PHPStan debt) and 5.2 (Pest baseline coverage) land first — flipping these gates live before those two land would immediately red every open PR against pre-existing, already-known failures. See Dependency Maps.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** CI workflow verification — this is a YAML/workflow change, not application code; verification is done by observing actual GitHub Actions run outcomes, not by writing Pest/PHPUnit tests.
- **Scenarios to prove each AC:**
  - AC #1: push a branch with a deliberate, throwaway PHPStan violation (e.g. an untyped param in a scratch file outside any module's real path) and confirm the `phpstan` job goes red; revert and confirm it goes green.
  - AC #2: push a branch with a deliberately failing test (or coverage artificially lowered) and confirm the `tests` job goes red on either failure or the `--min=82` floor; confirm it goes green on a clean run.
  - AC #3: inspect the repository's branch protection settings (or the documented handoff note if the dev agent cannot access them) and confirm `phpstan` and `tests` are listed as required checks.
  - AC #4/#5: diff `.github/workflows/ci.yml` and confirm only the `phpstan` and `tests` job steps changed — `pint` and `theme-build` steps are byte-identical to before.
  - AC #6: `git diff --stat laravel/phpstan.neon` produces no output.
- **Fixtures/mocks:** none — this story only edits a workflow YAML file; the MySQL `laravelpizza_test` service and Xdebug coverage driver are already configured by the existing `tests` job.
- **Edge cases:** a PR opened before this story lands (workflow file changes mid-PR) — confirm GitHub Actions re-evaluates the new job definition on re-run rather than using a stale cached one; a fork-based PR where `secrets`/service containers may behave differently than on `dev` pushes.

## Dependency Maps

- Blocked by: 5.1 (User/Lang PHPStan debt) — the `phpstan` job cannot be made blocking while User/Lang still fail, or every open PR turns red on pre-existing debt unrelated to the PR's own changes; 5.2 (Pest baseline coverage) — the `tests` job's `--min=82` floor cannot be enabled before a baseline at or above 82% is established.
- Blocks: none within Epic 5 — this is intentionally the last Epic 5 CI-facing story; per epics.md's Cross-Epic Dependencies, "Epic 5 (Code Quality) | All others | PHPStan L10 must pass before shipping any feature," so once this story lands, every other epic's PRs are subject to the same gate. [Source: docs/epics.md — Cross-Epic Dependencies]
- External: GitHub Actions (existing), repository branch-protection settings (may require GitHub admin access outside the dev agent's tooling).
