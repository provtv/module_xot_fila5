# 9.2: `Modules/Xot/_activity.code-workspace` non doveva esistere

**Status:** done — **Created:** 2026-08-27

## Perché quel file era sbagliato

Due violazioni della stessa regola, `docs/wiki/rules/module-theme-root-cleanup.md`
(Rule 2): *«Each module/theme root MUST have ONE `.code-workspace` file»*, con nome
`_<repo-semantic-name>.code-workspace` ricavato **dal remote**, non dal nome della
cartella.

1. **Nome di un altro modulo.** `_activity` dentro `Modules/Xot`: il workspace del
   modulo Activity in casa di Xot. Il remote di Xot è
   `git@github.com:laraxot/module_xot_fila5.git`, quindi il nome canonico è
   `_module_xot.code-workspace`. Un modulo non porta il workspace di un altro modulo,
   per lo stesso motivo per cui non ne porta le classi.
2. **Tre file dove ne serve uno.** La root di Xot aveva `_activity.code-workspace`,
   `_xot.code-workspace` e `_module_xot.code-workspace`.

## La trappola: il nome giusto aveva il contenuto sbagliato

`_module_xot.code-workspace` era il nome canonico ma conteneva uno **stub di una riga**
(`{"folders":[{"path":"."}],"settings":{}}`), mentre le 38 righe di impostazioni vere
(php-cs-fixer, phpmd, esclusioni) stavano nei due file dal nome sbagliato. Cancellare i
non canonici e basta avrebbe buttato via la configurazione tenendo il guscio.

Fatto invece: il contenuto delle 38 righe è stato portato **nel file dal nome canonico**,
poi i due non canonici sono stati rimossi. Copia di sicurezza già presente in
`docs/root-code-workspace-files/` — verificato byte per byte che i tre file avessero lo
stesso contenuto prima di rimuoverne due.

## Audit repo-wide: non era un caso isolato

Il `00-TRIGGER_MAP` rimandava a `bashscripts/tools/audit-module-theme-root-files.sh`
per far rispettare questa regola. **Quello script non esisteva.** Una regola senza gate
non è una regola: alla prima misura, 7 fra moduli e temi su 22 la violavano.

| Cartella | Prima | Dopo |
|---|---|---|
| `Modules/Xot` | 3 file, canonico ridotto a stub | 1, canonico con le impostazioni vere |
| `Modules/UI` | `_activity` (38 righe) + canonico stub | 1, canonico con le impostazioni vere |
| `Modules/Notify` | 2 identici | 1 |
| `Modules/Ptv` | 2 identici | 1 |
| `Themes/One` | 2 identici | 1 |
| `Themes/Zero` | 2, differivano per un a-capo finale | 1 |
| `Themes/Meetup` | 0 | **aperto**: nessuna `.git` propria, il tema contiene un solo file |

`Modules/UI` aveva **lo stesso `_activity.code-workspace`**: il file non era un incidente
di Xot, era una copia sparsa in più moduli.

## Lo script che mancava

`bashscripts/tools/audit-module-theme-root-files.sh` — scritto in questa story:

- ricava il nome canonico dal remote (`module_xot_fila5` → `_module_xot.code-workspace`),
  togliendo il suffisso `_fila<N>`;
- distingue **MANCANTE**, **DUPLICATI**, **NOME ERRATO** e **SENZA REPO**;
- usa `/bin/grep`, non `grep`: nelle sessioni degli agenti `grep` è una funzione che
  rispetta `.gitignore`;
- esce 1 se trova violazioni, così può stare in un gate.

Prima versione aveva un difetto trovato subito: per una cartella senza `.git` propria
`git -C` risale al repo padre e restituisce il nome del **progetto** invece che del
modulo (`Themes/Meetup` chiedeva `_base_ptvx.code-workspace`). Corretto con un controllo
`-e "$dir/.git"`.

## Acceptance Criteria

1. La root di ogni modulo/tema con repo proprio ha esattamente **un** `.code-workspace`, col nome ricavato dal suo remote.
2. Nessuna impostazione persa: dove il canonico era uno stub, ha assorbito il contenuto vero.
3. Esiste un gate eseguibile che verifica la regola ed esce diverso da zero sulle violazioni.
4. `bash bashscripts/tools/audit-module-theme-root-files.sh` → una sola violazione residua, `Themes/Meetup`, documentata.

## Verifiche

- audit: da **7 violazioni su 22** a **1**.
- `_module_xot.code-workspace` e `_module_ui.code-workspace` sono JSON validi (una volta tolti i commenti di riga, che il formato `.code-workspace` ammette) e contengono le 38 righe di impostazioni.

## `Themes/Meetup` — rimosso

Era l'ultima violazione dell'audit. Non aveva una `.git` propria, quindi il nome canonico
non era nemmeno ricavabile; conteneva **un solo file tracciato**
(`resources/mail-layouts/test-layout.html`) più tre cartelle `docs/` vuote, e non era
referenziato da nessuna config, nessun modulo, nessun documento. Su indicazione
dell'utente il tema è stato rimosso: la domanda giusta non era «che workspace gli diamo»
ma «deve esistere».

## Dove sta davvero il gate

Il `00-TRIGGER_MAP` rimandava a `bashscripts/tools/audit-module-theme-root-files.sh`.
Oltre a non esistere, **quel path non può esistere**: `bashscripts/.gitignore` riga 61
ignora `tools/`, quindi qualunque file scritto lì resta fuori dal repo. Il gate è stato
messo accanto agli altri, in `bashscripts/quality-gates/`, e il TRIGGER_MAP è stato
corretto in entrambe le righe che lo citavano.

Una regola può fallire in tre modi, e qui li ha fatti tutti e tre: lo script non c'era,
il path era ingestibile, e nessuno controllava il risultato.
