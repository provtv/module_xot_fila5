# Story 5.21: margine di type coverage

Status: ready-for-dev

## Story

Come **agente quality multi-modulo**,
voglio **portare a zero i 104 parametri senza tipo rimasti in `User`, `Xot` e
`IndennitaResponsabilita`**,
così che **il verde di `phpstan analyse Modules` smetta di dipendere da un margine di 14
parametri e non torni rosso su ogni file del perimetro al primo metodo scritto senza firma**.

## Perché questa story esiste, se il gate è verde

Misura di oggi, 2026-08-19 ore 21:30–21:55, con `load average 31`, 82 processi `phpstan`
concorrenti:

```bash
cd laravel
PHPSTAN_TABLE_ERROR_FORMATTER_FORCE_SHOW_ALL_ERRORS=1 \
  ./vendor/bin/phpstan analyse Modules --no-progress --memory-limit=-1 --error-format=json
```

→ **`file_errors: 0`**. Nessuna segnalazione da sistemare: la story 5.20 e la
[5.19](./5.19.pest-helpers-bootfiles-and-typecoverage.story.md) hanno chiuso i 535 errori del
baseline, e l'esito è già commentato sull'issue
[#79](https://github.com/laraxot/module_xot_fila5/issues/79).

Il problema è **quanto poco manchi a rifarlo rosso**. `typeCoverage.paramTypeCoverage` scatta
quando i parametri tipizzati scendono sotto il 99 % del **totale del perimetro**:

| grandezza | valore |
|---|---:|
| parametri totali nel perimetro (run 19:47) | 11 815 |
| soglia del pacchetto | 99 % |
| parametri senza tipo tollerati | ~118 |
| parametri senza tipo oggi | **104** |
| **margine** | **~14** |

Quattordici parametri. Una classe nuova con un costruttore a promozione non tipizzata, o un
test con tre closure senza firma, e l'errore ricompare — **non nel file che l'ha causato, ma
in tutti i file del perimetro**, perché la metrica è globale. Chi apre il gate il giorno dopo
vede centinaia di righe rosse e nessun indizio su chi le abbia prodotte.

Questa story compra il margine: 104 → 0 porta la tolleranza da 14 a 118 parametri.

## Acceptance Criteria

1. `cd laravel && ./vendor/bin/phpstan analyse Modules --no-progress --memory-limit=-1` →
   `[OK] No errors`, exit 0, **dopo `./vendor/bin/phpstan clear-result-cache`**.
2. Zero parametri senza type declaration nei tre moduli in perimetro, verificato con lo
   script di rilevazione (§ *Comandi*), su `app/`, `tests/`, `database/`, `config/`,
   escluse `docs/` e `*.blade.php` (fuori dal perimetro del neon).
3. `laravel/phpstan.neon` **non modificato** (AD-1). Nessun file `.neon` nuovo, nessuna
   baseline, nessun `@phpstan-ignore`, nessun `@var` inline, nessun cast di comodo (AD-8).
4. Ogni `mixed` dichiarato ha accanto il **motivo scritto**: o il nome del metodo genitore
   con firma non tipizzata che lo impone, o la ragione di dominio. Un `mixed` senza motivo è
   un fallimento dell'AC, non una scorciatoia accettata.
5. Nessuna guardia difensiva lasciata dove il tipo appena dichiarato la rende ridondante:
   il run per-file non deve produrre `function.alreadyNarrowedType`.
6. Per ogni `.php` toccato, la sequenza AD-17 completa: `php -l` → Pint → PHPStan sul file →
   PHPMD → PHPInsights. Evidence in `laravel/build/`, mai in `/tmp`.
7. `Modules/<Mod>/docs/` aggiornata dove il tipo dichiarato rivela un contratto implicito.
8. Coverage del modulo lavorato +10 % (AD-10), **se** il DB di test torna raggiungibile;
   altrimenti si riporta il blocco d'ambiente con la misura di `nc`, e l'AC resta aperto.

## Dev Notes

### La trappola che rende inutile la verifica per-modulo

`TomasVotruba\TypeCoverage\Rules\ParamTypeCoverageRule::processNode()` comincia con:

```php
if (! ScopeConfigurationResolver::areFullPathsAnalysed($scope)) {
    return [];
}
```

Se i path passati sulla riga di comando non coincidono con `parameters.paths` del neon
(`Modules/`), la regola **non emette nulla**. `phpstan analyse Modules/User` risponde
`[OK] No errors` con 91 parametri senza tipo dentro. Non è un bug da segnalare: è il
comportamento del pacchetto, e vale per tutte e cinque le regole `typeCoverage.*`.

Conseguenza operativa: il gate per-file di AD-17 **resta obbligatorio**, ma non serve a
verificare questa story. Serve a intercettare gli errori che il tipo appena aggiunto fa
emergere — `argument.type` (la firma reale non accetta quel tipo),
`function.alreadyNarrowedType` (le guardie difensive che servivano quando il parametro era
`mixed`). La verifica della story è **solo** il run completo su `Modules`.

### I `mixed` obbligati: firma del genitore non tipizzata

PHP consente a una classe figlia di **allargare** il tipo di un parametro, mai di
restringerlo. Dove il genitore Laravel non dichiara alcun tipo, il parametro vale `mixed` e
l'unica declaration compatibile è `mixed`. Verificato oggi in `vendor/`:

| Sito in `Modules/Xot` | Genitore | Firma del genitore |
|---|---|---|
| `GenerateModelClassCommand::getDefaultNamespace($rootNamespace)` | `Illuminate\Console\GeneratorCommand` | `getDefaultNamespace($rootNamespace)` — riga 283 |
| `GenerateModelClassCommand::replaceClass($stub, $name)` | idem | `replaceClass($stub, $name)` — riga 386 |
| `ApplicationError::toJson($options = 0)` | `Illuminate\Contracts\Support\Jsonable` | `toJson($options = 0)` — riga 13 |
| `HandlerDecorator::render($request, Throwable $e)` | `Illuminate\Contracts\Debug\ExceptionHandler` | `render($request, Throwable $e)` — riga 41 |
| `HandlerDecorator::renderForConsole($output, Throwable $e)` | idem | `renderForConsole($output, Throwable $e)` — riga 52 |
| `CustomRelation::get($columns = ['*'])` | `Illuminate\Database\Eloquent\Relations\Relation` | `get($columns = ['*'])` — riga 283 |

Sei degli undici siti di `Xot`. Qui `mixed` **è** la risposta corretta e non viola AD-8:
l'ultima spiaggia è tale perché il contratto a monte non lascia alternative. Scrivere
`Request $request` su `HandlerDecorator::render()` è un fatal a caricamento della classe, non
un miglioramento. Il `@param` con il tipo reale resta nel docblock — è lì che vive
l'informazione che PHP non può esprimere.

`UserContract::removeRole(...$role)` è il caso diverso: è un metodo di **interfaccia**, non un
override, e il docblock dichiara già
`string|int|array<int|string>|UserRole|Collection<int, UserRole>|\BackedEnum`. Lì la
declaration si può scrivere davvero; verificare prima che ogni implementazione la accetti
(`git grep -l "implements UserContract"`, poi le classi che dichiarano `removeRole`).

### Le closure Filament

Per `$record`, `$livewire`, `$records`, `$state`, `$data`, `$set`, `$get`, `$action` la
tabella dei tipi è in
[`filament-closure-param-types.md`](../wiki/concepts/filament-closure-param-types.md).
Tre regole che valgono anche qui:

1. Un parametro dichiarato e mai usato **si cancella**, non si tipizza: Filament inietta per
   nome, la closure può dichiarare solo ciò che le serve.
2. Il `@param` di una closure dentro una catena fluente va **dentro** la chiamata,
   immediatamente prima della closure. Messo sopra `->action(...)` PHPStan non lo legge.
3. Una closure che dichiara `$records` obbliga la bulk action a `->accessSelectedRecords()`,
   altrimenti Filament lancia `LogicException` a runtime.

### File in UPDATE che vanno letti prima di toccarli

Nessun file di questa story è NEW. Tutti sono UPDATE, e tre meritano una lettura completa
prima dell'edit perché il tipo non è la sola cosa in gioco:

- `Modules/User/tests/Fakes/FakeAgent.php` — 15 parametri in un fake: le firme devono restare
  compatibili con l'interfaccia che il fake sostituisce, altrimenti i test passano contro un
  contratto che non esiste. Verificare **quale** classe reale sta sostituendo prima di
  stringere qualsiasi firma.
- `Modules/Xot/app/Relations/CustomRelation.php` — relazione custom che estende `Relation`;
  `get()` è chiamato dal core Eloquent, non solo dal codice del progetto.
- `Modules/Xot/app/Exceptions/Handlers/HandlerDecorator.php` — sta nel percorso di
  rendering di **ogni** eccezione dell'applicazione. Un fatal qui non si manifesta come un
  test rosso, si manifesta come pagina bianca.

## Comandi

```bash
# cwd: laravel/
./vendor/bin/phpstan clear-result-cache
PHPSTAN_TABLE_ERROR_FORMATTER_FORCE_SHOW_ALL_ERRORS=1 \
  ./vendor/bin/phpstan analyse Modules --no-progress --memory-limit=-1 \
  --error-format=json > build/phpstan.json

# conteggio per modulo e per identifier
php -r '$j=json_decode(file_get_contents("build/phpstan.json"),true);
echo "TOTAL ",$j["totals"]["file_errors"],"\n";
$b=[];foreach($j["files"] as $f=>$d){foreach($d["messages"] as $m){
  $b[$m["identifier"]??"?"]=($b[$m["identifier"]??"?"]??0)+1;}}
arsort($b);foreach($b as $k=>$v)printf("%5d %s\n",$v,$k);'

# gate per-file (AD-17), su ogni file toccato
php -l <file>
./vendor/bin/pint <file>
./vendor/bin/phpstan analyse <file> --no-progress --memory-limit=-1
tools/phpmd.sh <file> text ../phpmd.xml
tools/phpinsights.sh analyse <file> --min-quality=80 --min-complexity=80 \
  --min-architecture=80 --min-style=80
```

Rilevazione dei parametri senza tipo, indipendente da PHPStan (utile perché la regola tace
sui sottopercorsi): scanner a `token_get_all()` che cerca `T_FUNCTION`/`T_FN`, salta
`docs/`, `vendor/`, `build/` e i `.blade.php`, e considera tipizzato un parametro che ha
almeno un token di tipo prima della `T_VARIABLE` — attenzione a **non** contare `&` come
tipo, o i parametri per riferimento risultano falsamente a posto.
