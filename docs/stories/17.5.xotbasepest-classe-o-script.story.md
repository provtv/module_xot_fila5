# 17.5: `XotBasePest` e' invocata come classe ma scritta come script

## Story

Come **sviluppatore che lancia la suite di un modulo qualsiasi**,
voglio **che `XotBasePest::assertListContains()` esista davvero**,
cosi' **i test che la chiamano arrivino alla prima asserzione**.

Questo non e' rumore dell'analizzatore: sono test che a runtime falliscono con
un errore di classe non trovata.

## Contesto misurato

Misura del 2026-08-24 su `analyse Modules`: 14 segnalazioni `class.notFound`.

```
Class Modules\Xot\Tests\XotBasePest not found
Call to static method assertListContains() on an unknown class Modules\Xot\Tests\XotBasePest
Call to static method assertThrows() on an unknown class Modules\Xot\Tests\XotBasePest
```

Distribuzione: Activity 6, Media 3, Tenant 2, Notify 1, User 1, Xot 1.

### La prova non e' il `grep`, e' il caricamento

Il file **esiste**:

```
Modules/Xot/tests/XotBasePest.php   6057 byte, 203 righe
```

L'autoload PSR-4 e' **corretto** — `Modules/Xot/composer.json` mappa
`Modules\Xot\Tests\` su `tests/`.

Eppure:

```bash
cd laravel && php -r 'require "vendor/autoload.php"; var_dump(class_exists("Modules\\Xot\\Tests\\XotBasePest"));'
# bool(false)
```

Motivo: il file non dichiara ne' `namespace` ne' `class`. E' un bootstrap Pest
procedurale — lo dice il suo stesso commento: «Bootstrap Pest condiviso di tutti
i moduli». Non manca la mappatura: manca la dichiarazione.

Chiamanti verificati: `Geo`, `Chart`, `User`, `Gdpr`, `CloudStorage`, `Notify`
e altri, sia in `tests/Pest.php` sia in file di test.

## Le due architetture, entrambe difendibili

| Opzione | Cosa comporta | Costo |
|---|---|---|
| **A — diventa una classe** | aggiungere `namespace Modules\Xot\Tests;` e racchiudere gli helper in `final class XotBasePest`, mantenendo gli helper procedurali dove servono a Pest | i `tests/Pest.php` che la includono come script vanno rivisti |
| **B — resta uno script** | i chiamanti smettono di trattarla come classe e usano le funzioni globali che il bootstrap gia' definisce | tocca ogni file chiamante |

La story **deve scegliere**, non lasciare le due forme mescolate: e' esattamente
lo stato attuale, ed e' la ragione del difetto.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `php -r 'require "vendor/autoload.php"; var_dump(class_exists("Modules\\Xot\\Tests\\XotBasePest"));'`
   restituisce `true`, **oppure** nessun file sotto `laravel/Modules` referenzia
   `XotBasePest` come classe. Uno stato o l'altro, mai i due mescolati.
2. La scelta fra A e B e' scritta nella story con la motivazione, prima di
   toccare il codice.
3. `analyse Modules` non riporta piu' `class.notFound` per `XotBasePest`.
4. **Almeno un test per ciascun modulo chiamante viene eseguito davvero e
   passa.** `php -l` non e' prova che un test giri; `phpstan` non e' prova che
   un test passi.
5. I test girano sulle repliche MySQL `*_test` con `DatabaseTransactions`.
   Nessun `RefreshDatabase`, nessun `migrate:fresh`, nessun `--force`.
6. Nessun file di test viene cancellato per far sparire una segnalazione.

- [ ] Applicare la scelta a tutti i chiamanti, senza lasciare forme miste (AC: #1)
- [ ] Eseguire la suite dei moduli chiamanti e registrare l'esito (AC: #4, #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **`class_exists()` e' l'unica prova.** Un `grep` che trova il file e un
  `composer.json` con la mappatura giusta portano entrambi alla conclusione
  sbagliata. Solo il caricamento decide.
- **I dati sono sacri.** Le repliche `*_test` sono MySQL reali, non SQLite usa
  e getta. Nessuna operazione distruttiva sul database, mai decisa dall'agente.
- **Il difetto e' invisibile oggi** perche' sepolto sotto 595 segnalazioni di
  configurazione. Dopo 16.8 e 17.3 diventa uno dei pochi rimasti: e' il motivo
  per cui quelle due vengono prima.

## Owned File/Module Scope

- `laravel/Modules/Xot/tests/XotBasePest.php`
- I `tests/Pest.php` e i file di test dei moduli chiamanti, limitatamente alle
  righe che referenziano `XotBasePest`
