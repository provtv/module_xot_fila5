# XOT-5.40 — convenzioni `.md` e gate sui file nuovi

## Story

Come agente che scrive documentazione in un repository da 35.866 file `.md`, voglio una
regola sola, verificabile da uno script, che dica **quando creare un file e quando
aggiornarne uno**, così da smettere di aggiungere la ventesima pagina sullo stesso
argomento.

## Le regole

1. **Prima di creare, cercare.** Un file nuovo si crea solo dopo aver verificato che
   nessuno tratti già l'argomento, e aver deciso — motivandolo — che aggiornare
   l'esistente sarebbe peggio.
2. **Niente date nei nomi file.** `sessione-2026-08-24.md` è sbagliato: la data sta nel
   frontmatter, dove è un dato; nel nome è un ostacolo alla ricerca e garantisce un file
   nuovo a ogni sessione.
3. **Frontmatter YAML completo**, non simbolico.
4. **Almeno 5 link relativi bidirezionali** per file: se A linka B, B linka A.
5. **Nel frontmatter, almeno un link a una issue GitHub e uno a una discussion**
   sull'argomento. Se non esistono, si creano **nel repository dove il file vive
   fisicamente** — `cd <cartella del file> && git remote -v`, non il repo di root.

## Perché, regola per regola

- **Cercare prima**: il repository ha 22 file che parlano di traduzioni e 15 di PHPStan,
  scritti perché era più veloce aprire un file nuovo che trovare quello giusto. Ogni
  duplicato aggiunge una versione che divergerà.
- **Niente date**: un nome con la data è un nome che nessuno riuserà. Produce
  `analisi-2026-08-24.md` e `analisi-2026-09-02.md` che dicono cose incompatibili senza
  che nessuna dichiari di superare l'altra.
- **Frontmatter**: è ciò che qmd indicizza. Senza, il file è cercabile solo per testo
  pieno, e `type`/`tags`/`module` non filtrano.
- **Cinque link bidirezionali**: un documento isolato non viene mai raggiunto. La
  bidirezionalità è la parte che costa: un link a senso unico si perde alla prima
  riorganizzazione.
- **Issue e discussion nel frontmatter**: legano il documento alla conversazione che lo ha
  prodotto. La issue dice *cosa* è stato deciso, la discussion *perché* e quali
  alternative sono cadute. Nel repo giusto, perché il modulo viaggia da solo.

## Baseline misurata (2026-08-24)

`/usr/bin/find` su `laravel/Modules`, `laravel/Themes`, `docs`, `bashscripts`:

| Metrica | Valore | Quota |
|---|---:|---:|
| File `.md` totali | 35.866 | 100% |
| Senza frontmatter | 17.885 | 49% |
| Con **zero** link relativi | 22.661 | 63% |
| Con almeno 5 link relativi | 3.792 | **10%** |
| Con una issue nel frontmatter | 3.528 | 10% |
| Con una discussion nel frontmatter | 3.339 | 9% |
| Con una data nel nome | 320 | 1% |

Distribuzione dei link relativi per file: 0 → 22.661 · 1 → 2.990 · 2 → 2.225 ·
3 → 2.582 · 4 → 1.616 · ≥5 → 3.792.

## La scelta di scala, dichiarata

Applicare le cinque regole a 35.866 file significherebbe, per la regola 5, **una issue e
una discussion per file**: oltre 70.000 oggetti GitHub. Non è fattibile né desiderabile —
sommergerebbe le issue vere e il rate limit dell'API renderebbe la campagna inaffidabile.

La lettura operativa è **per argomento, non per file**:

- ogni **argomento** ha una issue e una discussion nel repo che lo possiede;
- tutti i file `.md` che trattano quell'argomento puntano a quella coppia;
- se più file puntano alla stessa issue, è il segnale che vanno **fusi** — la regola 1 e la
  regola 5 si rinforzano a vicenda.

Con questa lettura la regola 5 non è burocrazia: è un rilevatore di duplicati.

## Acceptance Criteria

1. `bashscripts/docs/prompts/55-md-conventions.md` — oggi un file vuoto di 0 byte —
   contiene le cinque regole, il perché di ciascuna, gli esempi corretti e sbagliati, e la
   procedura per creare issue e discussion nel repository giusto.
2. Esiste `bashscripts/quality-gates/verify-md-conventions.sh` che, su un elenco di file o
   sul diff, verifica: data nel nome, frontmatter presente e con i campi obbligatori,
   almeno 5 link relativi, presenza di `github_issue` e `github_discussion`, e link
   relativi che risolvono a file esistenti.
3. Il gate ha una **modalità diff** (`--changed`) che controlla solo i file `.md`
   aggiunti o modificati rispetto a `HEAD`: è quella che si può rendere bloccante subito,
   senza aspettare la bonifica di 35.866 file.
4. Il gate è verificato in negativo su ciascuna delle cinque regole: un file con una data
   nel nome, uno senza frontmatter, uno con 4 link, uno senza issue, uno con un link
   relativo rotto — ognuno fa uscire `1` con il messaggio giusto.
5. Il gate distingue **errore** (regole 2, 3, 5: verificabili meccanicamente) da
   **avviso** (regola 4 sulla bidirezionalità, che richiede di leggere il file linkato).
6. La procedura per issue e discussion è eseguibile e documentata: `gh issue create` e la
   mutation GraphQL per le discussion (`gh issue view` è rotto qui, si usa `gh api`), con
   il repository ricavato da `git -C <cartella> remote -v`.
7. La regola è nel second brain in
   `docs/wiki/rules/markdown-documentation-standard.md`, aggiornata, non duplicata.
8. I 320 file con una data nel nome sono censiti in un elenco con il nome proposto senza
   data, pronto per la rinomina in una story successiva. Non si rinominano qui: ogni
   rinomina rompe i link entranti e va fatta con la riscrittura dei riferimenti.

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **`grep` e `find` sono funzioni di shell** che filtrano i path gitignored: nei gate
  servono `/bin/grep` e `/usr/bin/find`.
  [Source: laravel/Modules/Xot/docs/stories/5.37.zero-conflict-markers-repo-wide.story.md]
- **`gh issue view` è rotto** su questa installazione (fallisce su `projectCards`): si usa
  `gh api`. Le discussion sono raggiungibili **solo via GraphQL**.
  [Source: bashscripts/docs/prompts/18-github-issues.md]
- **Il repository giusto è quello della cartella, non della root.** Ogni modulo ha il suo
  remote: `git -C laravel/Modules/Notify remote -v` →
  `laraxot/module_notify_fila5`. Una issue aperta sul repo di root per un file di Notify è
  nel posto sbagliato e non viaggia col modulo.
- **Non rinominare i file con la data nel nome in questa story.** Ogni rinomina rompe i
  link entranti, e la riscrittura non è meccanica: lo stesso basename può essere il nome
  legittimo di un altro file in un altro modulo.
  [Source: docs/wiki/rules/docs-naming-audit-modules-themes.md]
- **Mai una riscrittura automatica di massa sulle docs**: è ciò che ha prodotto il fatal
  error del 2026-08-05 su `Modules`.
- **Il gate a repo intero sarebbe rosso su 32.000 file.** Per questo la modalità
  `--changed` è l'AC che conta: un gate che nessuno può far passare viene disattivato, e
  un gate disattivato è peggio di nessun gate.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Negativo, una prova per regola**: file con data nel nome; file senza frontmatter; file
  con frontmatter incompleto; file con 4 link relativi; file senza `github_issue`; file con
  un link relativo che non risolve. Ognuno deve uscire `1` e nominare la regola violata.
- **Positivo**: un file conforme scritto a mano esce `0`.
- **Modalità diff**: con un `.md` non conforme nel working tree, `--changed` lo trova; con
  il working tree pulito esce `0` senza scandire l'intero repository.
- **Costo**: `--changed` sotto i 5 secondi; la scansione completa non è nel percorso
  bloccante.
- **Non regressione**: `verify-llm-wiki.sh` resta `PASS`.

#### Due difetti trovati dal gate su sé stesso

Il primo file passato al gate è stato `55-md-conventions.md`, e ha fallito per due motivi
che erano difetti del **gate**, non del documento:

1. **Estraeva i link dai blocchi di codice.** Gli esempi «così no» (`/var/www/.../guida.md`)
   venivano contati come link rotti. Corretto: i fence e gli span di codice vengono tolti
   prima dell'estrazione.
2. **Conosceva una sola convenzione di frontmatter.** In questo repository ne convivono
   due: `type`/`created`/`updated` nelle docs di modulo, `document_type`/`created_at`/
   `updated_at` in `bashscripts/docs/prompts` (imposta da `YAML-FRONTMATTER-CONVENTION.md`).
   Il gate ora accetta entrambe le forme invece di imporne una e rendere non conforme
   metà repository per decreto.

disattivato, e un gate disattivato è peggio di nessun gate: `--changed` è la modalità

#### Censimento della regola 2

**308 file** con la data nel nome — non 320: il conteggio grezzo includeva 12 falsi
positivi (numeri di versione tipo `-1.4`). Distribuzione: Notify 72, User 70, `docs/` 45,
Xot 33, bashscripts 27, Activity 18, UI 11, Lang 10, Media 7.

**154 su 308 hanno una collisione**: il nome senza data esiste già nella stessa cartella.
Lì la rinomina non basta, serve prima una fusione. È metà del lotto, ed è la ragione per
cui l'AC #8 chiede l'elenco e **vieta** la rinomina in questa story.

#### Ostacolo che non posso rimuovere

Le **discussion sono disabilitate su `laraxot/base_ptvx_fila5`**. Finché restano spente,
nessun `.md` che vive nel repository di root può soddisfare la regola 5. Serve
un'abilitazione dalle impostazioni del repository, che richiede permessi di admin.
Verificate attive su: `module_xot_fila5`, `module_notify_fila5`, `module_user_fila5`,
`module_lang_fila5`, `theme_zero_fila5`, `bashscripts_fila5`.

#### Non fatto, dichiarato

- La bonifica dei 35.866 file esistenti: è una campagna a ondate, story separata.
- La rinomina dei 308 file datati: vietata da AC #8 finché non c'è la riscrittura dei link.
- L'aggancio di `--changed` a un hook pre-commit: va deciso con chi lavora sul tree, non
  imposto mentre altri agenti stanno scrivendo.
