# 5.5: Migration verification: test forward-only on rollback

**Story ID:** 5.5
**Epic:** 5 — Code Quality & Infrastructure
**Slug:** forward-only-migration-verification
**Status:** backlog

## Story

As a developer relying on the project's forward-only migration discipline,
I want an automated check that every migration's `down()` is a safe no-op and that migrations are idempotent on re-run,
so that forward-only migration safety is enforced by tooling instead of relying on every contributor remembering the "dati sacri" convention by hand.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A verification check inspects every `laravel/Modules/*/database/migrations/*.php` file and flags (by file path) any `down()` method containing `Schema::drop`, `dropColumn`, or `dropIfExists`. [Source: docs/wiki/rules/migration-filename-from-model-name.md — "Vietato: `down()` con `Schema::drop(...)` — perdita irreversibile su rollback accidentale"]
2. Running `php artisan module:migrate {Module}` twice in sequence against a test database produces zero schema errors and zero duplicate-column errors on the second run. [Source: docs/wiki/rules/migration-filename-from-model-name.md — "`tableCreate()` è no-op se la tabella esiste, `tableUpdate()` applica solo le colonne mancanti"]
3. The verification runs against a MySQL `*_test` replica database wrapped in `DatabaseTransactions`; it never invokes `RefreshDatabase`, `migrate:fresh`, or `migrate:refresh`. [Source: docs/wiki/rules/testing_no_refresh_database_critical.md — "Test in Pest sulle repliche MySQL `*_test`... isolamento con `DatabaseTransactions`"]
4. For each module, migration filenames are checked against the `{timestamp}_create_{model_plural_snake}_table.php` convention and flagged if derived from the physical table name instead of the model name. [Source: docs/wiki/rules/migration-filename-from-model-name.md — "N modelli = N migrazioni... derivato dal nome del modello, non dal nome fisico della tabella"]
5. The check is a reusable, documented command a developer or CI can invoke on demand, producing a pass/fail result per module. [Inference — no PRD/architecture text specifies exact tooling, but architecture.md's deployment strategy names "migration pre-checks" as a required CI gate input; this AC operationalizes that]

## Tasks / Subtasks

- [ ] Write `bashscripts/tools/quality/verify-migrations.sh` that scans all `Modules/*/database/migrations/*.php` `down()` bodies for `drop`/`dropColumn`/`dropIfExists` and exits non-zero listing violations (AC: #1, #5)
- [ ] Extend the same script (or a companion check) to derive the expected model class per migration filename and assert it resolves to an existing `\Modules\{Module}\Models\{Model}` class (AC: #4)
- [ ] Write a Pest test that runs `php artisan module:migrate {Module}` twice against the `*_test` MySQL replica inside `DatabaseTransactions`, asserting the second run raises no schema errors (AC: #2, #3)
- [ ] Document the script's usage and location in `bashscripts/docs/` per root script policy (AC: #5)
- [ ] Run the check across all existing modules; record any violations found without bulk-editing migrations to fix them (see Dev Notes scope note) (AC: #1, #4)

Vietati: "`add_*_to_*`, `update_*`, `modify_*`, `drop_*`, `fix_*`, `.old`, suffissi numerici. ## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Pest integration test wrapping the verification script's core logic (or invoking the script itself as a subprocess) plus a live double-migration idempotency check against a real test database.
- **Fixtures:** the MySQL `*_test` replica already configured for module testing; a deliberately "bad" migration fixture (down() with `Schema::drop`) created only inside the test's temp/fixture space — never committed to a real module's `database/migrations/`.
- **Scenarios to prove each AC:**
  - AC #1: feed the checker a fixture migration with an unsafe `down()`; assert it is flagged. Feed it a compliant migration; assert it passes.
  - AC #2/#3: pick one small, already-existing module; run `module:migrate` twice inside a `DatabaseTransactions`-wrapped test; assert no exception and no duplicate-column error on the second pass.
  - AC #4: feed the checker a fixture filename derived from a table name (e.g. `create_performance_mylog_table.php`) and assert it is flagged as a mismatch; feed it a compliant filename and assert it passes.
  - AC #5: run the documented command end-to-end and confirm it returns a per-module pass/fail summary with a non-zero process exit code when any module fails.
- **Edge cases:** modules with zero migrations (must pass trivially, not error); migrations relying on a Xot base class default `down()` (verify the base default is itself safe, since child migrations may not override it); modules already in `phpstan.neon`'s `excludePaths` (verification should still run — this check is independent of PHPStan).
