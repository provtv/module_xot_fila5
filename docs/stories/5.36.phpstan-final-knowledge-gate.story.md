# XOT-5.36 — consolidamento finale PHPStan, second brain e Graphify seriale

## Story

Come maintainer del quality gate globale, voglio consolidare in una sola esecuzione seriale
lo stato delle story, la conoscenza PHPStan e il grafo del repository, così che lo zero
finale sia riproducibile e supportato da evidenze navigabili.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Una baseline cold e seriale di `cd laravel && ./vendor/bin/phpstan analyse Modules --no-progress`
   termina con exit code `0`, stdout/stderr puliti e un artefatto di evidenza linkato dai documenti globali.
2. Tutte le story della campagna elencate in `bmad-output/sprint-status.yaml` sono riconciliate
   con il frontmatter owner-local; nessuna story `ready-for-dev`, `in-progress` o `review` viene
   dichiarata conclusa senza Dev Agent Record e gate richiesti.
3. Prima del gate sono censiti processi PHPStan/Graphify concorrenti e lock recenti/stale; nessun
   lock vivo viene rimosso e la corsa finale parte solo con writer globali assenti.
4. `graphify update .` viene eseguito una sola volta, serialmente, dopo il consolidamento docs e
   dopo il gate PHPStan; l'esito e i file Graphify aggiornati sono registrati con link di evidenza.
5. Le docs PHPStan canoniche dei Theme One, Zero e Three, il thread campagna, l'epic map, il piano
   parallelo e il second brain riportano la stessa baseline finale, le cause radice riusabili e i
   link alle story owner-local, senza duplicare docs dei moduli.
6. `phpstan.neon`, baseline, ignore, exclude e livello di analisi restano invariati; nessuna
   suppression o modifica applicativa è introdotta dalla story meta.
7. XOT-5.23 è riconciliata come predecessore storico del gate e punta a XOT-5.36; le evidenze
   finali includono almeno comando, timestamp, exit code, conteggi e link ai documenti aggiornati.

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- Lo zero globale è valido solo come corsa cold seriale: cache e writer concorrenti hanno già
  prodotto misure divergenti. [Source: bmad-output/architecture.md#adr-001-phpstan--solo-laravelphpstanneon]
- Lock recenti sono vivi per criterio temporale; il PID del lock può appartenere al subshell e
  non autorizza uno sblocco forzato. [Source: bmad-output/architecture.md#adr-005-coordinamento-multi-agente-e-lock]
- Il second brain è aggiornato a livello tema/globale in questa story; le docs module-local restano
  responsabilità dei rispettivi owner. [Source: bmad-output/architecture.md#adr-009-second-brain--docs-modulotema-obbligatori]
- La baseline iniziale della campagna era 5.711 file findings; le misure intermedie non sono una
  certificazione finale. [Source: docs/chat/phpstan-modules-regression-campaign.md#baseline-intermedia-dopo-wave-3]
- XOT-5.23 descrive i rischi di cache, formatter e surface delle estensioni; XOT-5.36 ne conserva
  il razionale ma possiede il consolidamento finale. [Source: laravel/Modules/Xot/docs/stories/5.23.phpstan-modules-zero-regression-guard.story.md#perché-lo-zero-è-fragile]
- Non eseguire Graphify prima della stabilizzazione: l'update globale è deliberatamente l'ultimo
  writer seriale della campagna. [Source: AGENTS.md#graphify]

  dei lock e censimento processi PHPStan/Graphify; allegare l'esito senza rimuovere lock vivi.
- Gate statico: cache pulita, una sola analisi `Modules`, output completo e exit code conservati;
  verificare esplicitamente stdout/stderr e assenza di processi concorrenti durante la misura.
- Reconciliation test: confronto meccanico tra status YAML e frontmatter delle story, più controllo
  che ogni story conclusa abbia Dev Agent Record non vuoto.
- Documentation test: link locali risolvibili, stessa baseline finale nei documenti owned, nessuna
  doc module-local modificata e nessun duplicato tematico introdotto.
- Safety diff: nessuna modifica a `laravel/phpstan.neon`, file baseline/ignore/exclude o codice
  applicativo; `graphify update .` avviene una sola volta e soltanto alla fine.

## Learnings from Previous Stories

- Un modulo verde non certifica il monorepo; il gate finale deve essere cold, globale e seriale.
- Gli status aggregati sono una vista: il frontmatter e il Dev Agent Record owner-local restano la fonte.
- Gli update Graphify concorrenti possono rendere il grafo incoerente; un solo update finale riduce il drift.
- Il second brain deve conservare cause e decisioni, non dump di errori o duplicati per modulo.
